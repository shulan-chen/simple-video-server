## 1. 你的理解是否正确？

你的理解**大体正确**，补充几个关键点：

### 容器 vs 虚拟机

```
┌─────────────────────────────┐    ┌─────────────────────────────┐
│         虚拟机 (VM)          │    │        容器 (Container)      │
├─────────────────────────────┤    ├─────────────────────────────┤
│  App A  │  App B  │  App C  │    │  App A  │  App B  │  App C  │
├─────────┼─────────┼─────────┤    ├─────────┼─────────┼─────────┤
│  OS(2G) │  OS(2G) │  OS(2G) │    │  Container Runtime (共享)   │
├─────────────────────────────┤    ├─────────────────────────────┤
│       Hypervisor            │    │         Host OS             │
├─────────────────────────────┤    ├─────────────────────────────┤
│         Hardware            │    │         Hardware            │
└─────────────────────────────┘    └─────────────────────────────┘
  每个VM独立一个OS，几GB起步            共享Host OS内核，几MB~几十MB
  启动时间：分钟级                      启动时间：秒级甚至毫秒级
```

**容器不是虚拟机**，它的本质是：
- 用 Linux 的 **namespace** 技术隔离进程（让进程"以为"自己是独立的）
- 用 Linux 的 **cgroups** 技术限制资源（CPU、内存上限）
- 用 **Union FS（联合文件系统）** 实现镜像分层

所以容器里跑的进程，**其实就是宿主机上的一个进程**，只是被隔离了视野。
这也是为什么容器比虚拟机快得多、轻得多。

### 核心概念三角

```
  Dockerfile  ──build──▶  镜像(Image)  ──run──▶  容器(Container)
  （建筑图纸）              （可执行包）              （运行中的实例）

  类比：
  Dockerfile  ──────▶  .exe 安装包   ──────▶  正在运行的程序
```

- **镜像**：只读的，可以存到仓库里分发（类似 npm 包）
- **容器**：镜像跑起来的实例，有自己独立的文件系统层（可读写）
- **Registry（镜像仓库）**：存储镜像的地方，公共的如 Docker Hub，公司自建如 Harbor

## 2. Dockerfile 详解

### 2.1 基本结构和最常用指令

Dockerfile 就是一系列「对镜像做什么操作」的指令，每一行指令都会生成一个**镜像层（Layer）**。

```dockerfile
# ──────────────── 最常用的 10 条指令 ────────────────

FROM golang:1.24-alpine          # 基础镜像（必须有，且必须第一条）

WORKDIR /app                     # 设置工作目录（后续命令的执行位置）

COPY go.mod go.sum ./            # 把宿主机文件复制进镜像
COPY . .                         # 复制当前目录所有文件

RUN apk add --no-cache git       # 在构建时执行命令（安装依赖、编译等）
                                 # 每个 RUN 都生成一个新层，尽量合并

ARG SERVICE_NAME                 # 构建时参数（docker build --build-arg 传入）
                                 # 只在构建阶段有效，不会保留在镜像里

ENV TZ=Asia/Shanghai             # 运行时环境变量（会保留在镜像里，容器启动后可读）

EXPOSE 8080                      # 声明容器监听的端口（仅文档作用，不实际开放）
                                 # 真正开放端口靠 docker run -p 或 compose ports

USER appuser                     # 切换运行用户（安全实践：不用 root）

HEALTHCHECK --interval=30s \     # 健康检查（Docker 会定期执行，判断容器是否健康）
  CMD curl -f http://localhost:8080/health/ready || exit 1

CMD ["/app/service"]             # 容器启动时执行的命令（只能有一个 CMD）
                                 # 用 JSON 数组格式，避免 shell 信号传递问题
```

> **ADD vs COPY**：COPY 只复制文件，ADD 还能解压 tar 包和从 URL 下载。
> 优先用 COPY，语义更清晰。

> **CMD vs ENTRYPOINT**：CMD 是默认命令，`docker run` 时可以覆盖；
> ENTRYPOINT 是固定入口，不容易被覆盖。生产中常用 ENTRYPOINT 定启动脚本，CMD 传参数。

### 2.2 本项目 Dockerfile 逐行解析

本项目 Dockerfile 最重要的技术是**多阶段构建（Multi-stage Build）**，解决 Go 镜像体积问题：

```dockerfile
# ════════════════ 阶段一：构建阶段 ════════════════
# 用带 Go 编译器的镜像（golang:1.24-alpine 约 300MB）
FROM golang:1.24-alpine AS builder
#                        ↑ 给这个阶段起名为 "builder"

RUN apk add --no-cache git make   # 安装编译依赖

WORKDIR /build

# ★ 关键优化：先只复制依赖声明文件，利用 Docker 层缓存
# 原理：Docker 每层都有缓存，如果这两个文件没变，
#       下面的 go mod download 就直接用缓存，不重新下载
COPY go.mod go.sum ./
RUN go mod download               # 下载依赖（耗时操作，缓存起来）

COPY . .                          # 再复制源代码（频繁变动的部分放后面）

ARG SERVICE_NAME                  # 接收外部传入的服务名（api/web/stream/scheduler）
ENV SERVICE_NAME=${SERVICE_NAME}

# 编译 Go 二进制
# CGO_ENABLED=0 → 禁用 C 绑定，生成纯静态二进制（能在 alpine 里跑）
# -ldflags "-s -w" → 去掉调试符号，二进制从 ~15MB 缩到 ~8MB
# GOOS=linux GOARCH=amd64 → 交叉编译目标平台
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags "-s -w" \
    -o /build/service \
    ./cmd/${SERVICE_NAME}/main.go

# ════════════════ 阶段二：运行阶段 ════════════════
# 用极简的 alpine 镜像（约 5MB），不含 Go 编译器！
FROM alpine:latest
#  ↑ 这里没有 AS，是最终镜像

RUN apk add --no-cache ca-certificates tzdata curl
# ca-certificates → HTTPS 请求需要根证书
# tzdata          → 时区数据（设置 Asia/Shanghai）
# curl            → 健康检查命令用

ENV TZ=Asia/Shanghai

# 安全：创建非 root 用户来运行服务
# 如果容器被入侵，攻击者得到的是低权限用户，而不是 root
RUN addgroup -g 1000 appuser && \
    adduser -D -u 1000 -G appuser appuser

WORKDIR /app

# ★ 核心：从 "builder" 阶段复制编译好的二进制
# 整个 Go 工具链留在 builder 层，最终镜像里没有！
COPY --from=builder /build/service /app/service

# 复制配置和模板（--chown 设置文件所有者）
COPY --chown=appuser:appuser config /app/config
COPY --chown=appuser:appuser templates /app/templates

RUN mkdir -p /app/logs && chown -R appuser:appuser /app

USER appuser    # 切换到非 root 用户

EXPOSE 8000 8080 9090 8001   # 声明端口（仅文档作用）

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health/ready || exit 1

CMD ["/app/service"]

# 最终镜像大小：~20MB（vs 不用多阶段构建的 ~800MB）
```

**多阶段构建的核心价值：**

```
构建阶段（builder）          运行阶段（最终镜像）
┌─────────────────┐          ┌─────────────────┐
│ Go 1.24 编译器   │          │ alpine 5MB      │
│ go.mod/go.sum   │          │ ca-certs        │
│ 所有源代码       │  只复制   │ curl            │
│ vendor/         │ ────────▶ │                 │
│ 编译中间产物     │ 二进制文件 │ /app/service ✓  │
│                 │          │                 │
│ ~300MB          │          │ ~20MB           │
└─────────────────┘          └─────────────────┘
    构建完丢弃                     推送/部署这个
```

### 2.3 层缓存机制（构建速度优化）

Docker 构建时，**每条指令生成一层，层可以缓存**。一旦某层内容变化，该层及之后的所有层都会重建。

```dockerfile
# ✗ 低效写法：源代码变动就重新下载所有依赖
COPY . .
RUN go mod download

# ✓ 高效写法：依赖声明没变就复用缓存
COPY go.mod go.sum ./   # 只有 go.mod/go.sum 变了才重新下载
RUN go mod download
COPY . .                # 源代码变了只重建这层之后的部分
```

**本项目的层缓存设计：**
```
层1: FROM golang:1.24-alpine  → 几乎不变，永久缓存
层2: RUN apk add git make     → 很少变，缓存
层3: COPY go.mod go.sum       → 加依赖才变，缓存
层4: RUN go mod download      → 同上
层5: COPY . .                 → 每次代码改动都触发
层6: RUN go build             → 随层5重建
```

## 3. docker-compose.yml 详解

### 3.1 docker-compose 是什么？解决什么问题

`docker run` 只能启动单个容器，参数很长：

```bash
# 手动启动一个容器，又臭又长
docker run -d \
  --name video-server-api \
  --network video-network \
  -p 8000:8000 \
  -e DB_ADDR=139.196.242.169:3306 \
  -e REDIS_ADDR=139.196.242.169:6379 \
  --restart unless-stopped \
  video-server-api:latest
```

**docker-compose 解决的问题**：用一个 YAML 文件描述**多个容器如何一起运行**，一条命令启动整套服务。

```bash
docker-compose up -d      # 一条命令启动所有服务
docker-compose down       # 一条命令停止并删除
docker-compose logs -f    # 查看所有服务日志
docker-compose ps         # 查看所有服务状态
```

### 3.2 本项目 docker-compose.yml 逐字段解析

以 `prometheus` 服务为例，完整讲解每个字段：

```yaml
version: '3.7'         # Compose 文件格式版本，决定支持哪些功能
                       # v1/v2/v3 是不同格式，不是 Docker 的版本

services:              # 定义所有服务（每个 service = 一个容器）

  prometheus:          # 服务名（在 Docker 网络内可以用这个名字访问）

    image: prom/prometheus:v2.51.0
    # ↑ 直接用现成的镜像（不需要 build）
    # 格式：仓库名/镜像名:版本标签
    # 如果没有 image，就需要 build 字段来构建

    # build 字段（和 image 二选一，或同时有）
    build:
      context: .             # 构建上下文（Dockerfile 相对路径的根目录）
      dockerfile: Dockerfile # 指定用哪个 Dockerfile
      args:                  # 传给 Dockerfile 的 ARG 参数
        SERVICE_NAME: api

    container_name: video-server-prometheus
    # ↑ 容器的实际名字，不写则自动生成（项目名_服务名_序号）

    ports:
      - "9091:9090"
      # ↑ 端口映射，格式：宿主机端口:容器内端口
      # 访问宿主机 9091 → 转发到容器内的 9090
      # 注意：stream-service 已占用宿主机 9090，所以 prometheus 映射到 9091

    environment:
      - GF_SECURITY_ADMIN_USER=admin
      # ↑ 注入环境变量（会覆盖镜像里 ENV 指令设置的值）
      # 也可以写成 key: value 格式

    volumes:
      - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      # ↑ 挂载文件/目录，格式：宿主机路径:容器内路径:权限
      # ro = read only（只读），不写则默认读写
      # 容器读的是宿主机上的文件，宿主机修改后容器立即生效

      - prometheus-data:/prometheus
      # ↑ 挂载"命名卷"（Named Volume）
      # 数据存在 Docker 管理的目录里，容器删除后数据不丢失
      # 适合数据库、时序数据库等需要持久化的场景

    command:
      - "--config.file=/etc/prometheus/prometheus.yml"
      # ↑ 覆盖镜像的 CMD，相当于给程序传命令行参数

    extra_hosts:
      - "host.docker.internal:host-gateway"
      # ↑ 在容器的 /etc/hosts 里添加记录
      # host-gateway 是 Docker 解析宿主机 IP 的特殊值
      # 让容器内部可以用 host.docker.internal 访问宿主机上的服务
      # 用途：prometheus 容器抓取宿主机上运行的 web-service 的 /metrics

    depends_on:
      - prometheus
      # ↑ 声明启动依赖，grafana 在 prometheus 启动后才启动
      # 注意：只保证启动顺序，不保证服务"已就绪"（就绪靠健康检查）

    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health/ready"]
      # ↑ 健康检查命令，exit 0 = 健康，exit 非0 = 不健康
      interval: 10s       # 多久检查一次
      timeout: 5s         # 单次检查超时时间
      retries: 3          # 连续失败多少次才标记为 unhealthy
      start_period: 30s   # 容器启动后多久才开始检查（给服务初始化时间）

    networks:
      - video-network
      # ↑ 加入哪个网络（同一网络内的容器可以用服务名互相访问）

    restart: unless-stopped
    # ↑ 重启策略
    # no              → 不自动重启（默认）
    # always          → 总是重启（包括手动停止）
    # on-failure      → 只在非0退出码时重启
    # unless-stopped  → 总是重启，除非手动 docker stop（推荐）

networks:
  video-network:
    driver: bridge
    # ↑ 创建一个自定义 bridge 网络
    # 同一网络内的容器可以用服务名当域名互访
    # 例如：web-service 可以直接 http://api-service:8000 访问 api 服务
    # 不在同一网络的容器互相隔离

volumes:
  prometheus-data:      # 声明命名卷（Docker 自动管理存储位置）
  grafana-data:
  mysql_data:
```

### 3.3 网络通信是如何工作的

这是 docker-compose 最有用的特性，容器间可以**用服务名当域名**互相访问：

```
                    video-network（Docker 虚拟局域网）
    ┌───────────────────────────────────────────────────────┐
    │                                                       │
    │  web-service          api-service      stream-service │
    │  (172.20.0.2)  ──────▶ (172.20.0.3)    (172.20.0.4)  │
    │                                                       │
    │  http://api-service:8000  ← web-service 这样访问 api  │
    │  http://stream-service:9090 ← web-service 这样访问 stream│
    │                                                       │
    └───────────────────────────────────────────────────────┘
                              │
                          外部访问只能通过
                          ports 映射的端口
                          localhost:8080 → web-service:8080
```

**dev 环境**（`docker-compose.dev.yml`）中的服务名解析：
- `api-service` 访问 MySQL：`DB_ADDR=mysql:3306`（直接用服务名）
- `web-service` 访问 api：`API_ADDR=http://api-service:8000`
- `prometheus` 抓取 web：`host.docker.internal:8080`（宿主机运行时用这个）

## 4. docker-compose 和 k8s 的关系

### 4.1 不是给 k8s 用的

**docker-compose 和 k8s 是两个独立的编排工具，没有直接关系**：

```
场景                    工具选择
─────────────────────────────────────────────────────────
单台机器，本地开发        docker-compose ← 你现在用的
单台机器，小规模生产      docker-compose（够用）
多台机器，需要自动扩容     k8s
多台机器，高可用          k8s
```

### 4.2 编排工具的层级

```
                    k8s（Kubernetes）
                  /        |        \
            集群管理    自动扩容    高可用
            多机调度    故障恢复    滚动发布

                    docker-compose
                  /        |        \
             单机编排    服务依赖    网络隔离
             快速启动    环境变量    数据卷

                    docker run
                  只管一个容器
```

### 4.3 k8s 用什么代替 docker-compose

k8s 用 YAML 描述资源，概念比 docker-compose 复杂得多：

```yaml
# docker-compose 的一个服务
services:
  api-service:
    image: video-server-api:v1.0
    ports:
      - "8000:8000"
    replicas: 2

# k8s 等价写法需要：
# 1. Deployment（管理副本）
# 2. Service（暴露端口）
# 3. ConfigMap/Secret（配置）
# 约 60 行 YAML 对比 10 行
```

**什么时候用 k8s**：
- 需要多台机器部署（单台机器 k8s 是杀鸡用牛刀）
- 需要自动水平扩容（流量高时自动加副本）
- 需要滚动发布（不停机更新）
- 需要自愈能力（节点挂了自动迁移）

**当前项目的建议**：现在用 docker-compose 完全够。如果以后要做成真正的生产服务，再考虑迁移到 k8s。有工具（Kompose）可以把 docker-compose.yml 转成 k8s YAML。

## 5. 生产常见做法

### 5.1 镜像版本管理

```bash
# ✗ 生产环境禁止用 latest 标签
docker pull myapp:latest     # latest 是什么版本？不知道！

# ✓ 正确做法：语义版本 + 构建信息
docker build -t myapp:1.2.3 .
docker build -t myapp:1.2.3-abc123f .   # 带 git commit hash
#                             ↑ 精确到哪次提交构建的

# 生产部署流程（CI/CD 自动化）
git push → CI 触发构建 → docker build -t registry.com/myapp:${GIT_TAG} .
                       → docker push registry.com/myapp:${GIT_TAG}
                       → 更新 k8s Deployment 的镜像版本
                       → k8s 滚动替换旧容器
```

### 5.2 镜像仓库（Registry）

```
公共仓库（免费）：
  Docker Hub：docker.io/library/nginx:latest
  GHCR：ghcr.io/username/myapp:v1.0

公司私有仓库（常见选型）：
  Harbor（自建，开源）
  阿里云 ACR
  AWS ECR
  腾讯云 TCR

本项目如果要推送镜像：
  docker tag video-server-api:latest registry.aliyuncs.com/mycompany/video-server-api:v1.0
  docker push registry.aliyuncs.com/mycompany/video-server-api:v1.0
```

### 5.3 配置和密钥管理

```yaml
# ✗ 不要把密钥写死在 docker-compose.yml 里
environment:
  - DB_PWD=hardcoded_password_123    # 会被提交到 git！

# ✓ 方式1：.env 文件（加入 .gitignore）
# .env 文件内容：
# DB_PWD=real_password_here
environment:
  - DB_PWD=${DB_PWD}    # compose 自动读取 .env 文件

# ✓ 方式2：Docker Secrets（生产推荐）
secrets:
  db_password:
    file: ./secrets/db_password.txt    # 文件存在安全的地方

# ✓ 方式3：k8s Secret / Vault（企业级）
```

本项目的 `config/config.json` 已经在 `.gitignore` 里了，这是正确的做法。

### 5.4 健康检查和优雅关闭（本项目已实现）

```yaml
# 健康检查让 docker-compose 知道服务是否真的就绪
# 本项目每个服务都有 /health/ready 端点
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health/ready"]
  interval: 10s
  timeout: 5s
  retries: 3
  start_period: 30s    # 给服务启动时间，避免还没初始化就被判定不健康
```

**优雅关闭**（本项目 `cmd/*/main.go` 已实现）：
```go
// 收到 SIGTERM（docker stop 发送的信号）时，不立即退出
// 而是等待当前请求处理完毕（默认 30 秒超时）
// 这样滚动发布时不会丢请求
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
server.Shutdown(ctx)
```

### 5.5 非 root 用户运行（本项目已实现）

```dockerfile
# 本项目 Dockerfile 中的安全实践
RUN addgroup -g 1000 appuser && \
    adduser -D -u 1000 -G appuser appuser
USER appuser    # ← 切换到低权限用户

# 为什么重要：
# 如果程序有漏洞被入侵，攻击者得到的是 uid=1000 的低权限 shell

```

### 5.6 多环境配置（本项目已实现）

```
本项目的多环境设计：
  docker-compose.yml      → 生产环境（连外部 MySQL/Redis）
  docker-compose.dev.yml  → 本地开发（自带 MySQL/Redis 容器）

使用方式：
  生产：docker-compose up -d
  开发：docker-compose -f docker-compose.dev.yml up -d

更进一步的做法（大厂常见）：
  docker-compose.yml          → 公共基础配置
  docker-compose.override.yml → 开发环境覆盖（自动叠加，不需要 -f）
  docker-compose.prod.yml     → 生产环境覆盖
  docker-compose.staging.yml  → 预发布环境覆盖
```

### 5.8 下一步：全容器化（docker-compose.dev.yml）

如果想让所有服务都跑在容器里（本地开发），用：

```bash
docker-compose -f docker-compose.dev.yml up -d
```

这个文件额外包含了：
- MySQL 8.0 容器（数据持久化到 `mysql_data` 卷）
- Redis 7 容器
- 服务间通过服务名访问（`DB_ADDR=mysql:3306` 而不是 IP）
- `depends_on` 确保 MySQL/Redis 健康后才启动应用服务

## 总结

| 概念 | 一句话 |
|------|--------|
| Dockerfile | 描述「如何构建镜像」的脚本 |
| 镜像（Image） | 只读的打包产物，包含程序和运行环境 |
| 容器（Container） | 镜像运行起来的实例，本质是被隔离的进程 |
| 多阶段构建 | 构建环境和运行环境分离，镜像从 800MB 变 20MB |
| docker-compose | 用 YAML 描述多容器编排，一条命令启停整套服务 |
| 命名卷（Volume） | Docker 管理的持久化存储，容器删除数据不丢 |
| 网络（Network） | 容器间的虚拟局域网，用服务名互相访问 |
| 健康检查 | Docker 定期探测服务是否就绪，配合 depends_on 使用 |
| k8s | 多机器集群编排，docker-compose 的高配版，学习成本高 |
