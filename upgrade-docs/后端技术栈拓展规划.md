## 二、业务场景扩展规划

> **核心原则**：先想清楚"为什么要加这个业务"，技术是业务复杂度自然带来的，而不是强行添加的。

### 2.1 当前业务的局限性

目前的业务链路极短：

```
上传视频 → 存 OSS → 记元数据 → 播放（生成预签名URL）→ 评论
```

这条链路只能练到最基础的 CRUD + 文件存储，无法触发大量高频技术场景。

---

### 2.2 推荐扩展的业务模块（按技术价值排序）

---

#### 模块 A：视频处理流水线（触发：消息队列 + 分布式事务）

**业务描述**：
视频上传后不能立即播放，需要经过：转码（生成多分辨率）→ 截取封面 → 审核 → 发布

```
用户上传原片
      │
      ▼
stream-service 存 OSS
      │ 发 MQ 消息
      ▼
transcode-service（新服务）── 转码 1080p/720p/480p
      │ 发 MQ 消息
      ▼
thumbnail-service（新服务）── 截取封面
      │
      ▼
review-service（可 mock）── 内容审核
      │ 通过后
      ▼
视频状态变更为"可播放"
```

**触发的技术点**：
- **消息队列（Kafka）**：上传成功 → 发消息 → 各下游异步消费，完全解耦
- **分布式事务（Saga 模式）**：转码失败需要回滚（删除 OSS 文件、回滚状态）
- **消息幂等性**：转码消息可能被重复消费，需要保证只处理一次
- **分布式锁**：防止同一个视频被并发重复转码

---

#### 模块 B：用户关注 + 消息通知（触发：消息队列 + 缓存高级用法）

**业务描述**：
用户可以关注 UP 主，UP 主发布新视频后，粉丝收到通知；点赞/评论也触发通知。

```
A 发布视频
   │ 发 MQ 消息（topic: video.published）
   ▼
notification-service（新服务）
   │ 查 A 的粉丝列表（可能几百万）
   ▼
   ├── 推送站内通知（写 DB）
   └── 推送 WebSocket 实时通知（可 mock）
```

**触发的技术点**：
- **消息队列**：发布/订阅模式（Pub/Sub），UP 主发布解耦通知
- **缓存击穿**：热门 UP 主粉丝列表 key 过期时，大量请求同时穿透到 DB
  - 解决：互斥锁重建缓存（singleflight）
- **缓存雪崩**：大量视频缓存同时过期
  - 解决：随机化 TTL + 热点数据永不过期 + 异步刷新
- **缓存穿透**：查询不存在用户的关注列表（恶意请求）
  - 解决：布隆过滤器（Bloom Filter）
- **分布式锁**：关注/取关的并发竞态（防止 follower_count 计数错误）

---

#### 模块 C：视频推荐 + 搜索（触发：Elasticsearch + 消息队列）

**业务描述**：
用户行为（播放/点赞/收藏）实时写入行为流，驱动搜索索引更新和推荐分数更新。

```
用户播放视频
   │ 发 MQ 消息（topic: user.behavior）
   ├──▶ click-counter-service  → 更新视频播放量（Redis HyperLogLog 去重）
   ├──▶ search-service         → 更新 Elasticsearch 热度分数
   └──▶ recommend-service      → 更新用户行为画像（可 mock 简单实现）
```

**搜索功能**：
```
用户搜索"游戏"
   → Elasticsearch 全文检索 video_info 索引
   → 支持：分词搜索、高亮、排序（热度/时间）、过滤（分类）
```

**触发的技术点**：
- **Elasticsearch**：全文搜索、倒排索引、分词、聚合统计
- **消息队列（事件流）**：用户行为解耦，多个下游消费同一行为流
- **Redis HyperLogLog**：UV 统计（播放量去重），内存极小
- **Redis ZSet**：热门视频排行榜（实时 TopN）
- **CQRS 思想**：写入行为 → 异步更新搜索/推荐（读写分离的更高层抽象）

---

#### 模块 D：会员支付系统（触发：分布式锁 + 幂等性 + 分布式事务）

**业务描述**：
开通会员可以看高清视频。购买行为涉及：扣款 → 开通权益 → 发通知，三步必须原子。

```
用户点击购买会员
   │
   ▼
order-service（新服务）── 创建订单（防重：分布式锁）
   │ Saga 编排
   ├──▶ payment-service（mock）── 扣款
   ├──▶ membership-service     ── 开通权益
   └──▶ notification-service   ── 发购买成功通知
```

**触发的技术点**：
- **分布式锁（Redis）**：防止用户重复点击购买（幂等性保证）
- **分布式事务（Saga）**：扣款成功但开通失败需要补偿（退款）
- **消息幂等性**：MQ 消息可能重复投递，幂等消费防止重复开通
- **接口幂等性**：HTTP 请求重试不能重复扣款（Token 机制 / 唯一订单号）

---

#### 模块 E：服务间通信升级（触发：gRPC + 服务注册发现）

**业务描述**：
随着服务数量增加，服务间 HTTP 调用变得不可靠（硬编码地址、无负载均衡）。

**改造方案**：

```
当前：web-service → HTTP → api-service（硬编码地址）

目标：
  所有服务启动 → 注册到 Consul/etcd
       │
  web-service → gRPC → 通过服务发现找 api-service 实例
                      → 客户端负载均衡（Round Robin）
```

**触发的技术点**：
- **服务注册发现（Consul 或 etcd）**：
  - 服务启动时注册自己的地址
  - 服务关闭时自动注销
  - 调用方订阅服务列表变化
- **gRPC**：
  - 替换 api-service ↔ stream-service 之间的 HTTP 调用
  - Protobuf 定义接口契约，强类型，性能比 JSON 高 5-10x
  - 流式 RPC（视频元数据批量查询）
- **客户端负载均衡**：多实例部署时，gRPC 内置 resolver 自动分发请求

## 三、完整技术栈图谱（大厂面试视角）

### 3.1 必须掌握（面试高频，视频项目都能练到）

```
分布式基础
├── 分布式锁（Redis SetNX / Redlock）       ← 模块 A/B/D
├── 分布式事务（Saga 补偿 / TCC）           ← 模块 A/D
├── 分布式链路追踪（Jaeger / OpenTelemetry）← 贯穿所有模块
└── 分布式配置中心（Nacos / etcd）          ← 模块 E

消息队列
├── Kafka 基础（Producer/Consumer/Topic）   ← 模块 A/B/C
├── 消息幂等性（消息去重）                  ← 模块 A/D
├── 消息顺序性（分区有序）                  ← 模块 A
└── 死信队列 / 重试队列                     ← 模块 A

缓存进阶
├── 缓存穿透（布隆过滤器）                  ← 模块 B
├── 缓存雪崩（随机 TTL + 热点不过期）       ← 模块 B
├── 缓存击穿（singleflight / 互斥重建）     ← 模块 B
├── Redis 数据结构活用（ZSet/HyperLogLog）  ← 模块 C
└── 本地缓存 + Redis 二级缓存               ← 模块 B/C

服务治理
├── 服务注册发现（Consul / etcd）            ← 模块 E
├── gRPC（Protobuf + 流式调用）             ← 模块 E
└── 负载均衡（客户端 / 服务端）             ← 模块 E

搜索
└── Elasticsearch（全文搜索 + 聚合）        ← 模块 C
```

### 3.2 加分项（能做出来直接加分）

```

├── CI/CD 流水线（GitLab CI / GitHub Actions）

云原生进阶
├── K8s 基础（Deployment / Service / ConfigMap）

└── Service Mesh 入门（Istio sidecar 注入）
```

## 四、实施路线图

> 按技术价值 × 实施难度排优先级

### 第一阶段（P0，核心基础，约 3-4 周）

```
Week 1-2：消息队列（Kafka）
  ├── 视频上传完成 → 发 kafka 消息
  ├── 新增 transcode-service 消费消息（mock 转码，实际更新视频状态）
  └── 实现消息幂等性（基于消息 ID + Redis 去重）

Week 3：缓存三大问题
  ├── 布隆过滤器防穿透（视频/用户 ID 是否存在）
  ├── 热门视频缓存击穿（singleflight 保护）
  └── 随机 TTL 防雪崩

Week 4：分布式锁
  ├── Redis SETNX 实现基础锁
  ├── 视频重复上传防重（锁 + 幂等检查）
  └── 关注/点赞计数并发安全
```

### 第二阶段（P1，服务治理，约 2-3 周）

```
Week 5-6：gRPC + 服务注册发现
  ├── 定义 video.proto 和 user.proto
  ├── api-service 和 stream-service 之间改 gRPC 调用
  ├── 引入 Consul，服务启动注册，关闭注销
  └── web-service 通过 Consul 做服务发现 + 负载均衡

Week 7：分布式链路追踪
  ├── 接入 Jaeger（OpenTelemetry SDK）
  ├── 每个服务注入 tracer middleware
  └── Grafana 集成 Jaeger 看完整调用链
```

### 第三阶段（P2，业务深度，约 3-4 周）

```
Week 8-9：Elasticsearch 搜索
  ├── video_info 同步到 ES 索引
  ├── 实现全文搜索接口（分词 + 高亮）
  └── 热门视频排行（ZSet + ES 聚合）

Week 10-11：分布式事务（Saga）
  ├── 视频处理流水线失败补偿
  └── 会员购买三步原子保证
```

### 第四阶段（P3，工程能力，持续进行）

```
CI/CD：GitHub Actions 自动构建 + 推镜像
数据库：MySQL 主从读写分离
K8s：将 docker-compose 迁移到 K8s（用 Kompose 转换后手动优化）
压测：k6 压测 + pprof 找瓶颈 + 优化
```

## 五、面试价值分析

> 大厂后端面试的核心考察点：**你是否真正用业务场景驱动了技术选型，并踩过坑**

### 高价值话题（完成上述模块后能深聊的点）

| 面试问题 | 你的项目支撑 |
|---------|------------|
| 如何保证消息不丢失、不重复消费？ | Kafka 幂等消费 + 死信队列 |
| 缓存穿透/雪崩/击穿怎么处理？ | 布隆过滤器 + 随机TTL + singleflight |
| 分布式锁怎么实现，有什么坑？ | Redis SETNX + 过期时间 + Lua 原子操作 |
| gRPC 和 HTTP 怎么选？ | 内部服务用 gRPC，外部用 HTTP，讲 Protobuf 优势 |
| 服务发现怎么做的？ | Consul 注册 + 健康检查 + 客户端负载均衡 |
| 如何保证接口幂等性？ | 唯一 Token + Redis 去重 + 数据库唯一键 |
| 链路追踪怎么实现的？ | OpenTelemetry + Jaeger，讲 Span/Trace/Context 传播 |
| 分布式事务怎么处理？ | Saga 补偿模式，讲清楚为什么不用 2PC |
| 如何设计一个高并发的点赞系统？ | Redis 计数 + 异步落库 + 防刷分布式锁 |

### 差异化竞争力（做完后的项目亮点）

1. **完整的可观测性**：日志 + 指标 + 链路追踪（三大支柱）全部有
2. **真实的分布式问题解决**：不是"知道概念"，而是"在代码里解决过"
3. **业务驱动技术**：每个技术都有对应的业务场景，不是堆砌
4. **生产级工程实践**：Docker 多阶段构建、健康检查、优雅关闭、CI/CD

## 六、技术选型建议

| 技术分类 | 推荐选型 | 备选 | 选择理由 |
|---------|---------|------|---------|
| 消息队列 | **Kafka** | RabbitMQ | 高吞吐、持久化、分区有序；面试问得更多 |
| 服务注册发现 | **Consul** | etcd/Nacos | Go 原生友好，HTTP API 简单，本地部署容易 |
| 分布式追踪 | **Jaeger** | Zipkin | OpenTelemetry 标准，Grafana 原生支持 |
| 搜索引擎 | **Elasticsearch** | MeiliSearch | 面试必问，生态最成熟 |
| 分布式锁 | **Redis（SETNX+Lua）** | Redlock | 先掌握单机版，再了解 Redlock 的争议 |
| gRPC | **原生 gRPC-go** | Twirp | 标准协议，面试通用 |
| 配置中心 | **etcd** | Nacos | 已用于服务发现可复用，轻量 |

## 七、一句话总结

> **不要追求"覆盖了多少技术"，而要追求"能把每个技术为什么用、怎么用、踩了什么坑"讲清楚。**
> 
> 完成第一、二阶段后，你的项目就已经能支撑大厂后端中级岗位的面试了。第三、四阶段能让你在高级岗竞争中有差异化优势。
